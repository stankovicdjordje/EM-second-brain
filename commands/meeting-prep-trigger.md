Use the obsidian-second-brain skill. Execute `/meeting-prep-trigger $ARGUMENTS`:

The argument is a person's name, optionally followed by `--deep` (the older full 4-transcript read, see `/meeting-prep` step 3e) - handle typos and partial matches, with the same owner's-own-manager special case as `/meeting-prep`. This command is the on-demand, single-person version of the `meeting-prep-daily-trigger` scheduled task: instead of waiting for its daily run (which sweeps every qualifying meeting on the calendar), run its exact data-gathering and note-writing logic right now, for just this person. Unlike `/meeting-prep`, the result goes into Obsidian as a file to review later, not into this chat.

1. Read `_CLAUDE.md` first if it exists in the vault root, then resolve the person's name against `Knowledge Base/People/` the same way `/direct-report` does (fuzzy match, confirm if ambiguous), applying the same owner's-own-manager special case as `/meeting-prep` if relevant.
2. Look up this person's next (or today's) weekly 1-on-1 on the owner's calendar, for the note's `**Meeting:**` line.
3. Gather the meeting history **log-first**, exactly as `/meeting-prep` step 3 does: read the person's Agenda Log (themes, Open agenda items, the 3 most recent meeting entries), compare the log's newest entry date against the newest 1-on-1 transcript on Google Drive (same naming convention as `/direct-report`), and read in full only the transcripts newer than the log - normally one, treated as the primary source. If the log is current, read no transcripts at all. `--deep` additionally reads up to the last 4 transcripts in full, and a person with no usable log falls back to the up-to-4-transcript read. A meeting counts once, even if both its log entry and its transcript were read.
4. Read that person's Profile Card and Skills Matrix in full, and scan `Tasks/📥 Backlog` and `Boards/Personal.md` for open items tied to them - cross-check against these, don't let them drive the note. Before compiling step 6, explicitly pull out the Profile Card's **"Where they're headed"**, **Strengths**, and **Growth watch** sections, exactly as `/meeting-prep` step 4 does - they anchor the compilation, not just background reading.
5. Cross-team knowledge cross-check, exactly as `/meeting-prep` step 5 does: pull 2-4 topic/skill keywords from this person's own Skills Matrix gaps and Profile Card "Where they're headed"/Growth watch, grep across `Knowledge Base/People/` (every team) for anyone whose card might document relevant knowledge, read only the shortlisted matches' relevant section in full to confirm a genuine dated match before using it in step 6, and skip entirely rather than force or fabricate a connection.
6. Build the same four prioritized checklists (Follow-ups / Challenges / Growth / Achievements) as `/meeting-prep` step 6, following `Templates/Meeting Prep Template.md`'s exact shape (fall back to `references/meeting-prep-template.md`) - including weighing Growth against "Where they're headed," calling out Achievements that play to a named Strength, and appending any confirmed cross-team match from step 5 to its relevant Growth/Challenge item (capped at 2 people), per that same step. **No duplicates, anywhere:** every item appears exactly once in the whole note - an item that is both a Follow-up and an open Agenda Log item, or both a Challenge and a Growth topic, is listed once, in the single bucket it fits best, with its source tagged (`source: log`/`transcript`/`both`), never repeated under another heading or under "Agenda log open items". **Suggested agenda:** after the buckets are built, pick the 5-7 highest-priority items (by recurrence, time pressure, risk, and fit with the Profile Card's "Where they're headed") and list them, in the order to raise them, in a `## Suggested agenda` section placed directly under Review status, each line tagged with its bucket (e.g. `- [ ] [Follow-ups] **(High, 2/3 meetings)** ...`). **Move** those items out of their buckets so they are not repeated. **Never pre-check any box** - every `- [ ]` stays unchecked for the owner to tick.
7. Write the note to `<that person's folder>/Meeting Prep/To Review/<YYYY-MM-DD> - <Person Full Name>.md`, matching the template exactly: frontmatter, a `## For future Claude` preamble stating how fresh the sourcing was (the Agenda Log wikilinked with its last-entry date, which of its entries were used, and which transcripts - if any - were read and why: e.g. "log current through 2026-09-29; no transcripts read", "log through 2026-09-29; 1 newer transcript read (2026-10-06)", "`--deep`: ...", or "no Agenda Log found - read the last 4 transcripts"; never pad if fewer meetings exist) and that nothing has been sent anywhere yet, the `**Meeting:**` and `**Meetings reviewed**` lines (listing every distinct meeting evidenced, newest first, each marked as log entry, transcript, or both; the frontmatter `meetings-reviewed` list matches), the `## Review status` master checkbox, then the four checklist headings as unchecked boxes. Include the `## Suggested agenda` section directly under `## Review status`, exactly as the template shows (all boxes unchecked, no item repeated elsewhere in the note).
8. **Agenda doc entry.** Make sure the person's running agenda Google Doc ("Notes - <Person> / <Owner> - Weekly/Biweekly") has an entry for this meeting's date, and create one if it doesn't. This is the only thing this command ever writes to Google Docs.
   - **Find the doc.** Take the link after `**Agenda doc (running notes):**` in the person's `*Agenda Log*.md` (the doc ID is the part after `/document/d/`). If there is no log or no such link, search Google Drive for a Google Doc titled like the calendar event for this pairing (`Notes - <First name> / Đorđe - Weekly`, or `- Biweekly`; try both). If still not found, say "agenda doc not found" in the output and skip this step - never create a new document.
   - **Check for the date.** Read the doc with the Docs read tool. The response is huge (100k+ characters) and may be saved to a file, so do not read it whole - extract only the entries: top-level paragraphs whose `namedStyleType` is `HEADING_2`, each starting with a date chip (`dateElement`, with a UTC `timestamp`). Convert each timestamp to Europe/Stockholm and keep the date. Note the doc's `revisionId` and the first tab's `tabId`. Entries are stacked newest first.
   - **Entry already there** (any entry dated the meeting date): do nothing. Never edit, fill or reorder an existing entry.
   - **Entry missing:** insert a new one directly above the newest existing entry (at that entry's heading `startIndex`, normally 1; start of the body if the doc has no entries yet), in the first tab, in one `update_doc` batch with `writeControl.requiredRevisionId` set to the revision just read - if it is rejected because the doc changed, re-read once, re-check for the date, and retry; if it fails again, stop and report it, never force it. The entry is plain text (the Docs connector cannot recreate Calendar's date, event-link and person chips), laid out like the existing ones:
     - Paragraph text, in order, with a leading tab marking each nesting level: `<D Mon YYYY> | <calendar event title>` (use the doc's own style, e.g. `13 Oct 2026`, `29 Sept 2026`), `Attendees: <Person Full Name>, Đorđe Stanković`, `Notes`, `<Person Full Name>`, `⇥Add your talking points here.`, `Đorđe Stanković`, `⇥Follow ups`, `⇥Personal`, `⇥Project/Team`, `⇥Company Related`, `Action items`, an empty paragraph, then one more empty paragraph as a separator. (Manager case: the first name is the manager's, e.g. `Jani Maljanen`.)
     - Request order: `insertText` of all the paragraphs at the insertion index; `updateParagraphStyle` to `HEADING_2` for the first paragraph and `NORMAL_TEXT` for every paragraph after it (the inserted text inherits the old heading's style); `updateTextStyle` italic on `Add your talking points here.` and not-italic/not-bold on the rest; if the calendar event's link is known, `updateTextStyle` with that link on the event-title part of the heading; then `createParagraphBullets` (`BULLET_DISC_CIRCLE_SQUARE`) **bottom-up**, because removing the leading tabs shifts later indices - first the empty paragraph after `Action items`, then one range from the first person's name through `Company Related` (the tabs set the sub-bullet levels). Leave the four sub-bullets empty: they are the owner's slots, filled later by hand or from `/meeting-prep-apply`.
   - If the doc's layout isn't recognisable (no `HEADING_2` date-chip entries, a different structure), skip and report it rather than guess.
   - Report one of: entry already there / entry created / agenda doc not found / skipped (layout or write problem).
9. Notify the owner: a message to the vault's configured meeting-prep notification channel (the same one `meeting-prep-daily-trigger` and `/meeting-prep-apply` use) plus a separate desktop push notification, naming the person and a count per bucket, with an Obsidian deep link to the new note and the agenda-doc outcome from step 8.
10. Report back briefly here in chat what was found and where the note was written - unlike the scheduled task, this was invoked live, so say so here too, even though the note itself is the main deliverable.

HARD RULES:
- Never write to, or modify, any person's actual Profile Card, Skills Matrix, Performance Review, AI Competency Framework, or Agenda Log file - this only ever produces a new note under `Meeting Prep/To Review/` plus a notification, and - only when it is missing - one new entry inserted at the top of the person's agenda Google Doc (step 8). It never edits or deletes existing content in that doc, and never creates a document.
- Never fabricate a meeting, a talking point, or a person's vault folder. If something can't be found, say so explicitly rather than guessing.
- Respect each person's own stated exclusion policy (health/family circumstances, other people's private details).

This does not replace `meeting-prep-daily-trigger` - that scheduled task (once enabled) keeps sweeping every qualifying meeting each morning regardless of whether this command also ran. This command exists for checking one person right now instead of waiting for the next scheduled run. Once the owner has reviewed and checked boxes in the resulting note, `/meeting-prep-apply <name>` compiles them into the actual talking-points list, exactly as it would for a note the daily trigger produced - this command and that scheduled task write to the same place in the same shape, so `/meeting-prep-apply` doesn't need to know or care which one produced any given note.
