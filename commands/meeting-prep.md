Use the obsidian-second-brain skill. Execute `/meeting-prep $ARGUMENTS`:

The argument is a person's name, optionally followed by `--deep` (see step 3) - handle typos and partial matches, and treat a request naming the owner's own manager (if the vault's `_CLAUDE.md` or calendar shows one, e.g. a recurring "weekly" 1-on-1 the owner attends as the non-organizer report) as a request for the owner's own upward-1:1 prep, using the owner's own vault folder instead of a direct report's.

This is the **live, chat-only** counterpart to `/meeting-prep-trigger`. Both pull the exact same data through the exact same process and follow the same `Templates/Meeting Prep Template.md` shape - the only difference is where the result goes. This command presents everything directly in this conversation and compiles the owner's picks into talking points right here; `/meeting-prep-trigger` writes the same checklist to an Obsidian file instead, for the owner to review later.

1. Read `_CLAUDE.md` first if it exists in the vault root, then resolve the person's name against `Knowledge Base/People/` the same way `/direct-report` does (fuzzy match across every team subfolder, confirm if ambiguous).
2. Look up this person's next (or today's, if same-day) weekly 1-on-1 on the owner's calendar, for the meeting time and video call link.
3. Gather the meeting history **log-first**: the person's Agenda Log is the main source, and raw transcripts are read only to cover what the log hasn't caught up with.
   - **3a. Read the log.** Find `*Agenda Log*.md` in the person's own folder (case-insensitive; the owner's own folder for the manager case). Read its "Recurring discussion themes" and "Open agenda items" sections plus its **3 most recent meeting entries** (newest first - Covered / Partially covered / Not covered / Action items, or the per-owner action-item lists some logs use; read by section heading, never by position, since log layouts differ between people). The date of its newest meeting entry is the **log date**.
   - **3b. Freshness check.** Search Google Drive for this pairing's 1-on-1 transcripts (the same naming convention `/direct-report` uses), sort by created time, and note the date of the newest meeting that has actually happened up to and including today (one held earlier today counts). This is a metadata lookup only - don't open anything yet.
   - **3c. Log behind (newest transcript is later than the log date):** read in full every transcript newer than the log date - normally one - and treat it as the **primary source** for what to raise. The log entries become pattern/trend context. If more than two transcripts are newer than the log, still read them all, and say in the output that the log is well behind (the owner should run `/direct-report` for that person).
   - **3d. Log current (newest transcript is the same date as the log date or earlier):** skip transcripts entirely. The log's latest entry is the primary source; the two before it are trend context.
   - **3e. `--deep`:** the owner asked for the older full read. Do 3a-3b as above, then also read up to the last 4 transcripts in full (a superset of 3c), weighted by recency exactly as the old behaviour: the newest is the primary source, the older ones are pattern/trend context.
   - **3f. No usable log** (no Agenda Log file, or one with no meeting entries yet): fall back to the old behaviour - read up to the last 4 transcripts in full, newest as primary source, fewer is fine if that's all that exists - and say so explicitly.
   - **A meeting counts once.** Log entries are themselves distilled from transcripts, so never count a meeting twice just because both its log entry and its transcript were read; where both exist, use the transcript for tone, wording and detail, and the log for what was planned versus covered.
4. Read that person's `<Person> - Profile Card.md` and `<Person> - Skills Matrix.md` in full, and scan `Tasks/📥 Backlog` and `Boards/Personal.md` for open items tied to them. Cross-check against these - don't raise something the vault already shows as resolved or applied. Before compiling step 6, explicitly pull out three Profile Card sections - they anchor the compilation, not just background reading: **"Where they're headed"** (frames what counts as a worthwhile Growth item and raises priority on any Follow-up/Challenge blocking or accelerating that direction), **Strengths** (calibrates Achievements - a win playing to a named strength is worth calling out as such - and keeps Growth items building on existing strength rather than generic), and **Growth watch** (the severity anchor for Challenges, see step 6).
5. Cross-team knowledge cross-check: from this person's own material in step 4 (Skills Matrix "Open gaps (live)," Profile Card "Where they're headed," and Growth watch), pull 2-4 concrete topic/skill keywords they're currently working toward or stuck on (e.g. "Playwright," "test automation," "AI-driven QA"). Grep across `Knowledge Base/People/` - every team, not just this person's own - for those keywords to shortlist anyone whose card might document relevant knowledge. Section names aren't uniform across facet-file styles (a direct report's Profile Card has "Strengths"; a peer/manager's lighter-weight card may instead have it under "Where they're headed" or a practice-context section), so match on content, not a fixed heading name. Read only the shortlisted people's relevant section in full to confirm it's a genuine, dated, documented match - not a loose keyword coincidence - before using it in step 6. Skip entirely if nothing is a close fit; never force a stretch connection or fabricate one. Respect each cross-referenced person's own stated exclusion policy - never surface something they've flagged private just because it happens to match a keyword.
6. Following `Templates/Meeting Prep Template.md`'s shape (fall back to this repo's `references/meeting-prep-template.md` if the vault has none yet), build four prioritized lists - **Follow-ups**, **Challenges**, **Growth**, **Achievements** - highest priority first. **Format every item as `**(<Priority>[, <recurrence>/<N> meetings])** <item description>` - the bold priority/recurrence tag ALWAYS comes first, never appended at the end of the line.** For Follow-ups and Challenges, always include how many of the meetings evidenced it recurred in (e.g. "2/3 meetings"), where `<N>` is the number of distinct meetings actually covered by step 3 (log entries read plus any newer transcripts read, or up to 4 under `--deep` or the no-log fallback) - never inflate it by counting a meeting once from its log entry and again from its transcript, and use the log's "first raised" dates on recurring themes as supporting evidence of age, not as extra meetings. Where an item came from the log, end its description with `(source: log)`, from a newer transcript with `(source: transcript <date>)`, or from both with `(source: both)`. An item sitting in the log's "Open agenda items" or "Not covered" across two or more meeting entries is a "planned but not discussed" item - the most likely to be quietly dropped - so rank it higher for Follow-ups and say how many meetings it has been carried (e.g. "carried 3 meetings"). For Challenges specifically, cross-check severity against any existing vault framing of the same issue (the Profile Card's growth-watch section from step 4, Performance Review, or AI Competency Framework) rather than reading severity off a single transcript mention alone, since an issue the vault already documents as long-running or escalating outranks a first-time mention; for Growth, weigh items against the Profile Card's "Where they're headed" section from step 4 - a growth item that moves the person toward their own stated direction ranks higher than a generic skill check-in; for Achievements, call out explicitly when a win plays to a Strength already named in their Profile Card (step 4). For a Growth (or occasionally Challenge) item with a confirmed cross-team match from step 5, append a sentence naming the person(s) with a wikilink and their specific dated evidence, e.g. "...worth connecting with [[<Teammate Name>]], who already built a similar workflow (<date>)." Cap at 2 cross-referenced people per item. Every item must trace back to something actually in the material read above, or an explicitly open task - never invent one. If a bucket is genuinely empty, say so rather than omitting it. Respect the log's own stated exclusions (e.g. compensation or other people's private details deliberately not logged) - the log is read-only input and is never edited here.
7. Present this checklist directly here in chat, **opening with one freshness line** so a stale prep is obvious - e.g. "Log current through 2026-09-29; no transcripts read" / "Log through 2026-09-29; 1 newer transcript read (2026-10-06)" / "`--deep`: log through 2026-09-29 plus 4 transcripts" / "No Agenda Log found - read the last 4 transcripts". Then the checklist, **numbered per item within each section** (not as literal markdown checkboxes - those aren't clickable in this conversation), e.g. "F1, F2 ... C1 ... G1 ... A1", and ask which of them the owner wants as talking points.
8. Once the owner replies with their picks, compile exactly those into a **grouped, multi-level nested outline** of talking points and questions, matching the owner's own personal meeting-agenda doc convention (theme bullets with nested sub-bullets underneath) - group by the checklist's own review categories (**Follow-ups, Challenges, Growth, Achievements**, in that order) as plain top-level bullets, only including a category if at least one of its items was picked; nest one bullet per picked item directly under its category, phrased as something to actually say out loud (a direct question addressed to the person, or a stated idea/suggestion), never a meta-instruction describing the act of asking; a further third-level sub-bullet only where an item has a genuine follow-on question or supporting reference. End with two fixed, unnested closing bullets, "Anything from your side?" then "Q/A". Present that compiled outline here in chat, in a fenced code block using plain `-` markdown bullets with 2-space indent per level, so the owner can copy-paste it straight into his Google Doc - this is the actual deliverable.
9. Nothing gets written to any vault file by this command - it is entirely a live conversation. If the owner wants any of this saved afterward, that is a separate, explicit request, not something this command does on its own.

HARD RULES:
- Never write to, or modify, any person's actual Profile Card, Skills Matrix, Performance Review, AI Competency Framework, or Agenda Log file - all of it is read-only input here.
- Respect each person's own stated exclusion policy (health/family circumstances, other people's private details) when deciding what's worth surfacing.
- Never fabricate a talking point beyond what the material actually supports.

This is the sibling to `/meeting-prep-trigger` the same way `/direct-report` is to `/direct-report-trigger`: same underlying data and template, live-and-interactive here vs. written-to-Obsidian-for-later there. See `references/meeting-prep-template.md` for the shared template shape both commands follow.

This command does not create or update any vault note, so the usual AI-first write rule does not apply to its own output. Its inputs still must be read faithfully: sources preserved verbatim, recency respected, nothing invented beyond what `references/ai-first-rules.md`'s sourcing standard would require of a written note.
